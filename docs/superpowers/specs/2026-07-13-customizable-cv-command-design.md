# Customizable `cv` command — design

**Date:** 2026-07-13
**Status:** Approved (design)

## Goal

Make the site's `cv` terminal command fully customizable: let the visitor choose
**which experiences, which projects, and which individual skills** appear in the
generated CV PDF. With no customization applied, the output is **byte-for-byte
identical to today's** (all 3 experiences, first 5 projects, all 14 skill groups).

## Today's behavior (baseline)

- `components/commands/renders/CCv.tsx` renders a mock `GET /api/cv` "API playground"
  card with two params (`lang`, `download`) and preview/download buttons that build
  `/api/cv?lang=<locale>[&download=1]`.
- `app/api/cv/route.tsx` reads `lang`/`download`, calls `getCvData(locale)`, renders
  the PDF via `CVDocument`.
- `lib/cv/cv-pdf.data.ts#getCvData(locale)` assembles the data: **all** `EXPERIENCES`
  (3), `PROJECTS.slice(0, 5)` (top 5 of 11), **all** `SKILLS` (14 grouped rows).
- Only consumer of `getCvData` is the API route. Only consumer of `CV_PREVIEW_URL`
  is the command card.

## Decisions (locked)

1. **Skills granularity:** individual skill values (e.g. `Next.js`, `React`), not
   whole groups. A group keeps only its selected values; a group with zero selected
   values disappears.
2. **Empty category drops the section:** deselecting every item in a category removes
   that whole section (heading included) from the PDF. A projects-less or skills-less
   CV is valid.
3. **Selector UI:** chip toggles (pills that toggle on click, wrapping), with per-category
   `all · none · reset` controls and a live `selected / total` count.

## URL contract (`/api/cv`)

Three new query params, in addition to `lang` and `download`. All use **include-list**
semantics (list what is IN), comma-separated:

| Param         | Meaning                                   | Default when absent      |
|---------------|-------------------------------------------|--------------------------|
| `experiences` | subset of experience slugs                | all experiences          |
| `projects`    | subset of project slugs (all 11 available)| first 5 projects         |
| `skills`      | subset of individual skill values         | all skill values         |

Rules:

- **Presence, not value, marks an explicit selection.** `parseSelection` uses
  `searchParams.has(key)`:
  - key **absent** → category default.
  - key **present** (including empty `experiences=`) → explicit selection; the value is
    split on `,`, trimmed, empties dropped, then intersected with the known set. An
    empty/all-invalid result → **empty selection → section dropped**.
- **The card omits a param when the current selection equals that category's default**
  (order-independent set equality), so the default share URL stays clean:
  `/api/cv?lang=en`.
- **Canonical ordering always.** The API filters the canonical constant arrays
  (`EXPERIENCES`, `PROJECTS`, `SKILLS` — in their declared/sorted order) by membership.
  Click order and param order never affect the PDF.
- **Robust parsing:** unknown/renamed slugs and skill values are silently ignored (URLs
  are ephemeral — always regenerated by the card).
- Skill values are globally unique across groups today, so filtering by value name is
  unambiguous; membership is still applied per-group, so a hypothetical future duplicate
  would simply be kept in both groups.

**Trade-off (accepted):** because skills default to *all*, customizing skills yields a
long URL that lists every kept value. The **default URL stays clean** (param omitted at
"all"), so only opt-in skill customization is verbose. Acceptable for an honest API
playground. (Alternative if ever wanted: encode skills as an *exclude* list.)

## Architecture

Isolated, testable units:

### 1. `lib/cv/cv-selection.ts` (new, pure, client-safe)

Single source of truth for param names + selection semantics, shared by client and
server. **No server-only imports** (only pulls from `lib/constants`), so it is safe to
import into the `"use client"` card.

- `CV_ENDPOINT = "/api/cv"`.
- Param name constants: `experiences`, `projects`, `skills`.
- `ALL_EXPERIENCE_SLUGS`, `ALL_PROJECT_SLUGS`, `ALL_SKILL_VALUES` — derived from the
  constants (canonical order).
- `DEFAULT_EXPERIENCE_SLUGS` (= all), `DEFAULT_PROJECT_SLUGS` (= first 5),
  `DEFAULT_SKILL_VALUES` (= all).
- `type CvSelection = { experiences: string[]; projects: string[]; skills: string[] }`
  — always normalized to canonical order.
- `serializeSelection(selection, { lang, download }) → string` — builds the URL, omitting
  any category whose set equals its default; omits `download` when false. Emits selected
  items in canonical order.
- `parseSelection(searchParams) → CvSelection` — presence-based per the URL contract;
  returns canonical-ordered, validated subsets; category default when key absent.
- Small helpers: `sameSet(a, b)`, `canonicalize(all, chosen)`.

### 2. `lib/cv/cv-pdf.data.ts#getCvData(locale, selection?)`

- New optional 2nd arg `selection?: CvSelection`. `undefined` → today's defaults
  (all experiences, `PROJECTS.slice(0, 5)`, all skills) — preserves current callers.
- When provided:
  - experiences: `EXPERIENCES.filter(e => selection.experiences.includes(e.slug))`.
  - projects: `PROJECTS.filter(p => selection.projects.includes(p.slug))` (all 11 eligible).
  - skills: map `SKILLS`, keep each group's `values` filtered to `selection.skills`, then
    **drop groups whose filtered values are empty**.
- Everything else (education, languages, hobbies, links, summary, header) unchanged.

### 3. `app/api/cv/route.tsx`

- Parse the three params via `parseSelection(searchParams)`, pass to `getCvData(locale, selection)`.
- `lang`/`download` handling unchanged.

### 4. `components/cv-pdf/CVSections.tsx`

- `ExperienceSection`, `SkillsSection`, `ProjectsSection` each `return null` when their
  data array is empty, so an emptied category drops (heading included). Other sections
  unchanged.

### 5. `components/commands/renders/CCv.tsx`

- Holds three `Set<string>` selection states, seeded to the defaults from `cv-selection`.
- Imports `EXPERIENCES`, `PROJECTS`, `SKILLS` for slugs/values and `useTranslations("CV")`
  for experience/project display names and skill-group labels. Skill chip labels are the
  raw values (proper nouns, not translated).
- Builds the URL with `serializeSelection`.
- Renders (below the existing `lang`/`download` params) three chip selectors:
  - **experiences** — flat chips (display name), header with count + `all · none · reset`.
  - **projects** — flat chips (display name), header with count + `all · none · reset`.
  - **skills** — grouped: a category header (count + `all · none · reset` over *all* skill
    values), then per skill-group a small sub-label and its value chips.
- `reset` restores that category's default; `all` selects everything; `none` clears.

### 6. `components/commands/renders/CvParamChips.tsx` (new, presentational)

- Reusable pieces: a `Chip` toggle button (active/inactive styles matching the card) and
  a `CvParamSection` header (title, `n / total` count, `all · none · reset` controls).
- Experiences/projects use a flat chip list; skills compose the same `Chip` under
  per-group sub-labels.

### 7. i18n (`messages/*.json`, all 22 locales)

- Add `Commands.cv` keys: `selectAll`, `selectNone`, `reset`, and category labels
  `experiences`, `projects`, `skills`.
- Chip labels reuse existing `CV.experiences.*`, `CV.projects.*`, `CV.skillGroups.*`.

## Testing

- **`tests/unit/lib/cv-selection.test.ts` (new):** `serializeSelection` omits defaults
  (clean URL at defaults), emits canonical order, encodes subsets; `parseSelection`
  presence-based (absent→default, empty→dropped), ignores unknowns; round-trip stability.
- **`tests/unit/lib/cv-pdf-data.test.ts` (new or extend):** `getCvData(locale, selection)`
  filters experiences/projects/skills, drops emptied skill groups, `undefined`→defaults.
- **`tests/unit/api/cv.test.tsx` (extend):** route forwards parsed selection to `getCvData`;
  default request unchanged.
- Run `bun test`, `tsc --noEmit`, `biome check`.

## Out of scope (YAGNI)

- No selectors for education, languages, hobbies, or links (always all — request named only
  experiences/projects/skills).
- No reordering of items; canonical order only.
- No persistence of selections (URL is the only state; ephemeral).
